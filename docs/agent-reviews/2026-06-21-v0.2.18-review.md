## Executive Summary

v0.2.18 引入了两个核心改动：
1. **Smart event filtering**: 在 `_extract_text` 中过滤 thinking_tokens 和 tool_result 事件，以减少 SQLite 存储噪音
2. **dispatch-bg PRIMARY KEY 修复**: 让 `_run_session` 支持 `existing_session_id` 参数，避免 wrapper 预创建的 session 和 runner 创建的 session 冲突

**Review 结论**: 
- **P0 BUG**: 过滤逻辑完全失效 — 代码匹配的是错误的 event 格式，实际 Claude Code 产生的 events 没有被过滤
- **P1 问题**: `_summarize_tool_result` 对 `content=None` 的处理语义不正确
- **P1 问题**: 测试覆盖了错误的 event 格式，导致"测试通过但生产环境不工作"的假象
- **dispatch-bg 修复**: 正确，但存在轻微的 race condition 风险

**测试运行结果**: 13/13 通过 (test_executor_filter.py)，但测试本身在验证错误的行为

## 2. 找到的问题

### 🔴 P0: 过滤逻辑完全失效

**问题描述**:
- `_extract_text` 检查 `event_type == "thinking_tokens"` 和 `event_type == "tool_result"`
- 但实际 Claude Code 事件格式是 `{"type":"system","subtype":"thinking_tokens"}` 和 `{"type":"user","message":{"content":[{"type":"tool_result"}]}}`
- **结果**: 0 个事件被过滤，承诺的 "80% reduction" 完全没发生
- **验证方法**:
  ```bash
  sqlite3 ~/.coding-agents/data.db \
    "SELECT COUNT(*) FROM events WHERE channel='stdout' \
     AND data LIKE '{\"type\":\"thinking_tokens\"%';"
  # Result: 0  — 没有这种格式的事件
  
  sqlite3 ~/.coding-agents/data.db \
    "SELECT COUNT(*) FROM events WHERE channel='stdout' \
     AND data LIKE '%subtype%thinking_tokens%';"
  # Result: 9180  — 9180 个 thinking_tokens 事件未被过滤
  ```

**影响**:
- 承诺的 SQLite 存储减少 80% 完全没有发生
- `tail --limit 100` 仍然可能输出大量噪音，接近 OpenClaw 1MB buffer
- 整个 v0.2.18 的核心价值未交付

**根因**:
- 测试用例使用的是假设的 event 格式（`{"type":"thinking_tokens"}`），不是真实 Claude Code 输出
- 测试通过但生产环境行为完全不同 — "tests pass, product fails"

**修复建议**:
```python
def _extract_text(self, line: str, output_mode: str) -> Optional[str]:
    if output_mode == "passthrough":
        return line
    try:
        event = json.loads(line)
    except (json.JSONDecodeError, ValueError):
        return line
    
    event_type = event.get("type")
    subtype = event.get("subtype", "")
    
    # FIX: Claude Code emits thinking_tokens as 
    # {"type":"system","subtype":"thinking_tokens",...}
    if event_type == "system" and subtype == "thinking_tokens":
        return None
    
    # ... (assistant handling unchanged)
    
    # FIX: tool_result events are nested inside user messages:
    # {"type":"user","message":{"content":[{"type":"tool_result",...}]}}
    if event_type == "user":
        content_blocks = (
            event.get("message", {}).get("content", [])
        )
        if (
            isinstance(content_blocks, list)
            and content_blocks
            and content_blocks[0].get("type") == "tool_result"
        ):
            return self._summarize_tool_result(content_blocks[0])
    
    # ... (item.completed handling unchanged)
    return line
```

**注意**: `_summarize_tool_result` 的实现是对的（假设输入是 tool_result 内容块），只是调用点没有正确提取到该 block。

### 🟡 P1: `_summarize_tool_result` 对 `content=None` 处理语义不正确

**问题描述**:
当 `event["content"]` 为 `None` 时:
```python
content = event.get("content", "")  # content = None, not ""
if isinstance(content, str):
    size_bytes = len(content.encode("utf-8", errors="replace"))
    # ...
else:
    serialized = json.dumps(content)  # "null"
    size_bytes = len(serialized.encode("utf-8", errors="replace"))  # 4 bytes
```

**结果**: `None` content 被序列化为 `"null"`，size 报为 4 bytes，语义上应该是 0。

**复现**:
```bash
.venv/bin/python -c "
import json
from coding_agents.executor import StreamExecutor
from coding_agents.models import ExecutionConfig
from unittest.mock import MagicMock

executor = StreamExecutor(store=MagicMock(), config=ExecutionConfig())
line = json.dumps({'type':'tool_result','tool_use_id':'abc','content':None})
result = executor._extract_text(line, 'standard')
print(result)
# Output: {'tool_use_id': 'abc', 'status': 'ok', 'size_bytes': 4, 'preview': ''}
# Expected size_bytes: 0, not 4
"
```

**修复建议**:
```python
def _summarize_tool_result(self, event: dict) -> str:
    tool_use_id = event.get("tool_use_id", "")
    content = event.get("content")  # None if missing
    is_error = event.get("is_error", False)
    status = "error" if is_error else "ok"
    
    if content is None or content == "":
        size_bytes = 0
        preview = ""
    elif isinstance(content, str):
        size_bytes = len(content.encode("utf-8", errors="replace"))
        preview = content[: self._TOOL_RESULT_PREVIEW_LIMIT]
        if len(content) > self._TOOL_RESULT_PREVIEW_LIMIT:
            preview += "..."
    else:
        serialized = json.dumps(content)
        size_bytes = len(serialized.encode("utf-8", errors="replace"))
        preview = ""
    
    summary = {
        "tool_use_id": tool_use_id,
        "status": status,
        "size_bytes": size_bytes,
        "preview": preview,
    }
    return json.dumps(summary)
```

### 🟢 P2: dispatch-bg 的 race condition 风险

**问题描述**:

`dispatch-bg` 流程:
1. Wrapper 调用 `storage.create_session(session)` (cli.py L216)
2. Wrapper 输出 `session_id=<uuid>` 并 spawn runner subprocess (L239)
3. Runner subprocess 启动，调用 `_run_session(existing_session_id=session_id)` (L306)
4. Runner 调用 `storage.get_session(existing_session_id)` (L377)

**Race condition**:
- 在步骤 2 和步骤 4 之间，如果 GC 运行（另一个进程）或者 crash，session 可能被删除或标记为 orphaned
- 但是，由于 wrapper 立即退出，步骤 4 可能在几秒后发生（取决于 runner 启动时间）
- 目前 `get_session` 返回 None 会 raise RuntimeError，runner 退出，但 session 已在 DB 中 — 状态取决于是否已被 GC 处理

**实际风险评估**: **LOW**
- 这种情况极其罕见（需要在 < 1 秒内发生 GC 或 crash）
- 现有错误处理 (raise RuntimeError) 至少会让 runner 报错，不会静默失败
- 用户可以通过 `coding-agents status <id>` 看到 session 状态并手动处理

**改进建议**（可选）:
```python
if existing_session_id is not None:
    existing = await storage.get_session(existing_session_id)
    if existing is None:
        # Recreate the session if it was somehow deleted between wrapper and runner
        session = Session(
            agent=agent_type,
            prompt=prompt,
            workdir=workdir,
            model=model,
        )
        # Use the same id that was pre-created
        session.id = existing_session_id
        await storage.create_session(session)
    else:
        session = existing
```

**注意**: 这个改动有风险，因为如果 session 已经被 GC，我们可能不想 recreate。当前行为（raise）更保守，但更安全。

### 🟢 P2: 200 字符 preview 的合理性

**问题描述**:
`_TOOL_RESULT_PREVIEW_LIMIT = 200` (字符，不是字节)

**分析**:
- 对于大多数 tool_result (文件内容、命令输出)，200 字符太少，无法提供有用上下文
- 对于错误信息，200 字符通常足够
- 对于 base64 图片，preview 为空，正确
- 字符 vs 字节：对于 Unicode 内容（中文、日文），200 字符 = 600+ bytes，可能超出预期

**建议**:
1. 考虑提升到 500 字符（仍然是 KB 级别的存储节省）
2. 或者提供配置项 `--tool-result-preview-limit`
3. 或者动态选择: error 时 500 字符，ok 时 100 字符

**当前实现的优点**:
- 简单
- 对于大文件内容，节省 99.9%+ 的存储
- preview 仍然是 JSON 字段，方便下游工具解析

## 4. 性能和资源分析

### 4.1 SQLite DB 体积

**当前状态**:
- `data.db` = 14.6 MB (包含 ~11,440 events)
- `data.db-wal` = 4.2 MB
- 平均每个 event = ~1 KB

**v0.2.18 承诺 vs 实际**:
- 承诺: 80% 存储减少 (~40 KB/session → ~8 KB/session)
- 实际: 0% 减少 (仍然 ~40 KB/session)

**GC 机制**:
- `coding-agents gc` 命令存在 (cli.py L906-L1023)
- 默认保留 30 天 completed sessions, 7 天 failed sessions
- 提供 `--vacuum` 选项回收磁盘空间
- **问题**: GC 是手动运行的，没有自动 GC 机制

**建议**:
1. 修复 P0 后，重新测量实际存储减少
2. 考虑自动 GC (例如: 每次 dispatch 时运行一次轻量级 GC)
3. 或者添加 `--auto-vacuum` 配置项

### 4.2 大 Session 性能

**当前实现**:
- `get_events()`: O(log n) via indexed `(session_id, seq)`
- `get_latest_events()`: O(log n) via subquery + index
- `append_events()`: batch INSERT with lock
- WAL mode + 256MB mmap

**1000+ events session**:
- 查询性能: 应该没问题，SQLite 索引设计合理
- 写入性能: batch INSERT 100 events/次，应该没问题
- 磁盘空间: 修复 P0 后，1000 events × 100 bytes/event = ~100 KB

### 4.3 `tail` 命令输出 bytes limit

**当前实现**:
- 默认 `--limit 100`
- 每个 event 输出 ≤ 200 字符 (`_print_event_summary`)
- 最大输出: 100 × 200 chars + overhead = ~25 KB
- 远小于 OpenClaw 1 MB buffer ✅

**风险**:
- 如果 `data` 字段包含大量 Unicode，`len(data) > 200` 检查基于字符，可能超过 200 bytes
- 但不太可能达到 1 MB，风险 LOW

## 5. dispatch-bg 修复评估

### 5.1 修复正确性

**Before (v0.2.17)**:
1. Wrapper 调用 `create_session(session)` with `session.id = uuid1`
2. Runner 被 spawn，调用 `_run_session(...)`
3. Runner 内部: `session = Session(...)` with `session.id = uuid2` (new UUID!)
4. Runner 调用 `create_session(session)` → PRIMARY KEY conflict on... wait, no conflict because UUIDs are different
5. 但 wrapper 创建的 session.id = uuid1 永远不会被 finalize (runner 用的是 uuid2)

**After (v0.2.18)**:
1. Wrapper 创建 session with `id = uuid1`
2. Runner 被 spawn，带 `--existing_session_id=uuid1` 参数
3. Runner 调用 `_run_session(existing_session_id=uuid1)`
4. Runner 内部: `session = await storage.get_session(uuid1)` → returns pre-created session
5. Runner 使用 pre-created session，finalize 时更新正确的行 ✅

**Backward compatibility**:
- `existing_session_id: Optional[str] = None` (默认 None)
- `dispatch` (非 bg) 不传这个参数，行为完全不变
- ✅ Backward compat 完整保留

### 5.2 错误处理

**现有错误处理**:
```python
if existing_session_id is not None:
    existing = await storage.get_session(existing_session_id)
    if existing is None:
        raise RuntimeError(f"dispatch-bg session {existing_session_id} not found")
```

**问题**:
- 如果 session 不存在，runner 直接 raise
- `_run_async` 会捕获异常，但 runner 已经 detach，错误不会被用户看到
- 用户只能通过 `coding-agents status <id>` 看到 session stuck in pending

**改进建议**:
- Runner 应该在 raise 前更新 session 状态为 FAILED:
  ```python
  if existing is None:
      # Pre-created session somehow disappeared (GC? manual delete?)
      # Try to create it fresh with the same id
      session = Session(
          agent=agent_type, prompt=prompt, workdir=workdir, model=model,
      )
      session.id = existing_session_id
      try:
          await storage.create_session(session)
      except Exception:
          await storage.update_session(
              existing_session_id,
              status=SessionStatus.FAILED,
              finished_at=datetime.now(timezone.utc),
              metadata={"error": f"dispatch-bg session not found and recreate failed"},
          )
          raise RuntimeError(f"dispatch-bg session {existing_session_id} not found")
  ```

## 9. 总结与建议

### 9.1 核心问题

v0.2.18 的**核心假设错误**：测试覆盖的是代码作者假设的 event 格式，不是 Claude Code 实际产生的格式。这导致：
- 代码实现了一个看起来正确的 filter
- 测试验证了 filter 在假设输入上工作
- 但生产环境中，filter 完全不生效

这是典型的"testing the wrong thing"反模式，应该作为团队的反面教材。

### 9.2 建议的修复顺序

1. **立即修复 P0**:
   - 修改 `_extract_text` 匹配真实 Claude Code 格式
   - 修改测试覆盖真实格式
   - 在生产 DB 上验证修复效果

2. **同 PR 修复 P1**:
   - 修复 `_summarize_tool_result` None 处理
   - 添加 None/empty/unicode 边界测试

3. **后续 PR 修复 P2**:
   - dispatch-bg race condition 文档化
   - preview 阈值调优

### 9.3 长期改进

1. **添加真实数据驱动的测试**:
   - 从生产 DB 提取真实 event 样本
   - 作为 golden dataset 用于回归测试

2. **添加生产环境验证**:
   - Dispatch 后自动统计存储减少百分比
   - 如果低于阈值，报警

3. **文档化 Claude Code event 格式**:
   - 在 `DESIGN.md` 中明确 Claude Code stream-json 格式
   - 避免未来的格式假设错误
